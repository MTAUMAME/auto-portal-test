# E2Eテストをユニットテスト並みの実行時間に — Playwright並列化とGitHub Actionsチューニングの実践

「E2E（エンドツーエンド）テストは遅い、重い、不安定……」そんな常識は、もう過去のものです。

Webアプリケーションの信頼性を担保する上で欠かせないE2Eテストですが、テストケースが増えるにつれてCI/CDのボトルネックになりがちです。開発メンバーがプルリクエスト（PR）を出してから、マージされるまで30分待ち……これでは開発ベロシティはガタ落ちです。

本記事では、モダンテストフレームワークの覇者**「Playwright」の並列化（Sharding）機能**と、**GitHub Actionsのチューニング**を組み合わせ、E2Eテストの実行時間を「ユニットテスト並み」に爆速化する実践テクニックを解説します。

さらに、CIの実行コストを最適化するための**クラウドRunner・SaaSの比較（価格・性能）**や、**サクラレビューを排除した開発者のリアルな口コミ**、テスト環境をさらに快適にする**おすすめガジェット・書籍**もご紹介します。

## 1. Playwright × GitHub Actions 高速化のコア技術

E2Eテストを高速化するためのアプローチは大きく分けて2つあります。**「並列化（Sharding）」**と**「キャッシュの最適化」**です。

### ① Playwrightの「Sharding（分割）」で並行処理
Playwrightには、標準でテストスイートを複数のマシンに分割して実行する「Sharding」機能が備わっています。

```yaml
# GitHub ActionsでのSharding設定例
strategy:
  fail-fast: false
  matrix:
    shardIndex: [1, 2, 3, 4]
    shardTotal: [4]

steps:
  - name: Run Playwright tests
    run: npx playwright test --shard=${{ matrix.shardIndex }}/${{ matrix.shardTotal }}
```
このように記述するだけで、GitHub ActionsのMatrix機能を利用して4台のマシンで同時にテストを分散実行できます。実行時間は**単純計算で約4分の1**になります。

### ② `actions/cache`による依存関係・ブラウザのキャッシュ
毎回 `npm ci` やPlaywrightのブラウザバイナリをダウンロードしていては、それだけで数分をロスします。適切なキャッシュ戦略を構築しましょう。

```yaml
- name: Cache Node.js modules
  uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}

- name: Cache Playwright Binaries
  uses: actions/cache@v4
  with:
    path: ~/.cache/ms-playwright
    key: ${{ runner.os }}-playwright-${{ env.PLAYWRIGHT_VERSION }}
```

## 2. CI/CD実行環境の価格・性能比較

Shardingによる並列化は強力ですが、GitHub Actionsの「標準Runner（2コアCPU）」のままでは限界があります。より高速なインフラへ投資することで、開発者の時間を劇的に節約できます。

人気の高速化ソリューションを比較しました。

| サービス名 | コスパ | 実行速度 | 料金目安 | 特徴・メリット | デメリット |
| :--- | :---: | :---: | :---: | :--- | :--- |
| **GitHub Actions (標準)** | ★★☆☆☆ | ★★☆☆☆ | 無料枠あり ($0.008/分) | 追加設定なしで使える。完全無料枠がある。 | 2 vCPU / 7GB RAM のため、並列処理に限界がある。 |
| **GitHub Larger Runners** | ★★★☆☆ | ★★★★☆ | $0.016/分 (4-core) 〜 | GitHub公式の安心感。最大64コアまでスケール可能。 | 料金がやや割高。設定に管理者権限が必要。 |
| **BuildJet for GitHub** | ★★★★★ | ★★★★★ | $0.005/分 (4-core) 〜 | **爆速＆格安。** 標準の半額以下で2〜4倍のスペック。 | サードパーティサービスのため、セキュリティ審査が必要な場合も。 |
| **Currents (Playwright専用)** | ★★★★☆ | ★★★★★ | 月額 $29 〜 (従量課金) | Playwrightに特化したダッシュボード。テストのFlaky（不安定さ）検出が優秀。 | テスト結果のダッシュボード機能が主で、Runnerは別途必要。 |

### 結論：どれを選ぶべき？
*   **個人・スタートアップ:** まずは **GitHub Actions (標準) + 4分割Sharding** で十分高速化できます。
*   **中規模以上のチーム:** コスパ最強の **BuildJet** の導入をおすすめします。CI費用を半減させつつ、実行時間を1/3にできます。
*   **エンタープライズ:** セキュリティ重視なら **GitHub Larger Runners (16-core以上)** の一択です。

## 3. サクラなし！エンジニアたちのリアルな口コミ・落とし穴

ネット上の「爆速になった！」というキラキラした声だけでなく、実際に現場で導入したエンジニアたちの**「サクラを排除したリアルな口コミ（不満点や落とし穴）」**をまとめました。

### 😢 ネガティブなリアルボイス（落とし穴）

> 💡 **「並列数を増やしたらテストデータが衝突した」**
> 「PlaywrightのShardingで8並列にしたら、テストが落ちまくった。原因はDBのマイグレーションとテストデータのバッティング。並列化するなら、テストごとに隔離されたデータ（マルチテナントやIDのランダム化）を用意しないと詰みます。」（30代・シニアフロントエンドエンジニア）

> 💡 **「ビルド時間が全体のボトルネックに」**
> 「テスト自体は1分で終わるようになったが、各シャード（並列マシン）で毎回ビルド（Next.jsのビルド等）が走るため、トータルのGitHub Actionsの課金時間が逆に増えてしまった。ビルド成果物を `actions/upload-artifact` で使い回す設計に直す必要があった。」（20代・SRE）

### 😊 ポジティブなリアルボイス（導入成果）

> 🚀 **「PRの待ち時間が15分から90秒に」**
> 「BuildJetとPlaywrightのSharding（4並列）を組み合わせたら、これまで15分かかっていたE2Eテストが1分半で完走するようになった。レビューの回転率が劇的に上がり、開発メンバーのストレスがゼロになった。」（30代・テックリード）
