## 1. なぜ今話題になっているのか？

結論から言うと、**「`localStorage` に置いたJWTは、XSS（クロスサイトスクリプティング）攻撃によって一瞬で盗まれるから」**です。

SPA（Single Page Application）が爆発的に普及した2010年代半ばから、現在の2026年に至るまでのトレンドの変遷（時系列）を整理すると、Cookie回帰の理由がよく見えてきます。

```
【時系列で見る認証トレンドの変遷】

[2010年代半ば：SPA黎明期とJWTの爆発的普及]
・React/Vueの登場に伴い、ステートレスな「JWT + localStorage」が手軽さから大流行。
・「サーバー側にセッションを持たなくていいのでスケールしやすい！」と大絶賛される。
  ▼
[2010年代後半：「localStorageは危険」論争の激化]
・npmパッケージのサプライチェーン攻撃や、悪意あるスクリプト挿入（XSS）によるトークン窃盗被害が多発。
・「JavaScriptからアクセスできる場所にトークンを置くのはNG」という認識がセキュリティ界隈で常識に。
  ▼
[2020年代前半：SSR（Next.js等）の台頭とBFFパターンの確立]
・Next.jsやNuxtなどのサーバーサイドレンダリングが主流化。
・「HttpOnly」「Secure」「SameSite」属性を付与したCookieなら、JavaScriptからアクセスできずXSSに強いことが再評価される。
・APIとフロントの間に「BFF（Backend-for-Frontend）」を挟み、セキュアにCookieを処理する構成がデファクトスタンダードへ。
  ▼
[2024年〜2026年（現在）：サードパーティCookie規制の完了と「認証SaaS」の成熟化]
・ブラウザによるサードパーティCookie規制が完全定着。
・自前で「安全なファーストパーティCookieの制御」や「BFF」を実装するのは難易度が高すぎるため、
  安全なCookieハンドリングを自動で行ってくれる「Clerk」「Auth0」「Supabase」などの外部サービスを導入するのが現在の最適解に。
```

セキュリティの脆弱性は、ひとたび漏洩事故を起こせば企業の信頼を失墜させ、巨額の損失を生みます。「自前で下手にセキュアなCookie認証を書く」よりも、**実績のある認証SaaSを導入して、コア機能の開発にリソースを集中させるのが2026年現在のスマートな開発戦略**です。
