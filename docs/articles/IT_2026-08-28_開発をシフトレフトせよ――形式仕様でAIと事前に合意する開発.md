## 1. なぜ今「シフトレフト」と「形式仕様」なのか？

### シフトレフトとは？
システム開発の工程（要件定義 ➔ 設計 ➔ 実装 ➔ テスト）において、**品質保証やテスト、仕様のすり合わせを「より早い段階（左側）」で行うこと**を指します。

### AI開発における「形式仕様での事前合意」
AIにいきなり「〇〇のコードを書いて」と指示するのは、新人のプログラマーに口頭で曖昧な指示を出して丸投げするようなものです。

そうではなく、コードを書かせる前に**「状態遷移」「入力と出力の定義」「満たすべき不変条件（ルール）」を構造化したテキスト（形式仕様）**として記述し、AIに読ませます。そして、

> **「この仕様にロジックの破綻やエッジケース（例外）の漏れはありませんか？ 合意できたら教えてください」**

とAIと「事前合意」を取るのです。

これにより、AIは仕様の矛盾を自ら指摘し、完璧に理解した状態でコードを生成するため、**手戻り（デバッグ）がほぼゼロ**になります。

## 2. 実践！AIと「事前合意」するための簡易テンプレート

AIに仕様を理解させるための、今日から使えるシステム仕様定義の記述例（Markdown形式）です。

```markdown
# システム名: ユーザーポイント決済システム

## 1. システムの状態（States）
- [通常状態] -> 残高 >= 0
- [一時凍結] -> 不正検知システムが作動した場合

## 2. 不変条件（Invariants: 常に満たすべきルール）
- ユーザーのポイント残高がマイナスになってはならない。
- 1回の決済額は、その時点の保有ポイント以下でなければならない。

## 3. アクションと事前・事後条件
### アクション: ポイント消費（ConsumePoint）
- **事前条件（Pre-condition）**:
  - アカウントが[通常状態]であること。
  - 消費ポイント数 > 0 であること。
  - 保有ポイント >= 消費ポイント数 であること。
- **事後条件（Post-condition）**:
  - 新しい保有ポイント = 旧保有ポイント - 消費ポイント数。

---
【AIへの指示】
上記仕様に論理的な矛盾、または「決済中に通信が切断された場合」などの例外処理の漏れがないかレビューしてください。
仕様に合意できたら「合意しました」と述べ、上記仕様を完全に満たすTypeScriptのコードを出力してください。
```
