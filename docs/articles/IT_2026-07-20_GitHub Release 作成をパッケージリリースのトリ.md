## 1. なぜ「GitHub Release作成」をトリガーにしてはいけないのか？

理由は大きく分けて3つあります。

### ① 「リリース作成」と「パッケージビルド」の順序が逆転する（鶏が先か卵が先か問題）
GitHub Releaseを作成するということは、すでにそのバージョン（タグ）が確定している状態です。しかし、その後に走るCI/CDビルドで「テストが落ちた」「ビルドが失敗した」となった場合、**「GitHub上にはリリースが存在するのに、npmやPyPIにはパッケージが存在しない」という不整合**が発生します。

### ② ドラフト（下書き）やプレリリースの制御が複雑化する
`release: [published]` は、下書き（Draft）を公開したときにもトリガーされます。プレリリース（Pre-release）のつもりが本番環境にデプロイされてしまった、といった事故が多発します。

### ③ セキュリティ上のリスク（OIDCとプロベナンスの欠如）
最近のモダンなパッケージ管理（npmやPyPI）は、**OIDC（OpenID Connect）**を用いたパスワードレスな認証と、ソースコードが改ざんされていないことを証明する「Provenance（プロベナンス）」の署名を推奨しています。これらは「特定のGit Tagのプッシュ」や「信頼されたワークフロー（GitHub Actions環境）」をトリガーにする方が強固なセキュリティを担保できます。

## 2. 【これが正解】モダンな自動リリースフローの設計

AIコーディングアシスタント（GitHub CopilotやCursor）にワークフローを書かせる際も、以下の設計を指示しましょう。

### 推奨構成：`Semantic Release` または `Changesets` の導入
1. **GitHub Actions上でビルド・テストが100%成功することを確認する。**
2. **メインブランチへのマージをトリガーに、パッケージの自動バージョンアップとnpm/PyPIへのパブリッシュを実行する。**
3. **パブリッシュ成功後に、GitHub Actions側から「GitHub Release」を自動生成する。**

これなら、パッケージの公開が成功した時のみ、GitHub Releaseが作成されるため、不整合は絶対に起きません。
