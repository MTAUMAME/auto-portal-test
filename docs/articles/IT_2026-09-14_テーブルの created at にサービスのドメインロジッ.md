## 1. 話題のブログ「めもるが」の記事要約
**「テーブルの created at にサービスのドメインロジックを持たせない」**

多くの開発者がやってしまいがちなアンチパターン、それが**「レコード作成日時（`created_at`）を、サービスのビジネス上の日付（例：会員登録日、注文確定日）として使い回す」**ことです。

### なぜ`created_at`をドメインロジックに使ってはいけないのか？

| 問題点 | 発生する具体的なトラブル |
| :--- | :--- |
| **データの移行・インポート** | 過去データを移行する際、移行作業時の日時が`created_at`に入ってしまい、ユーザーの「本当の登録日」が消失する。 |
| **仮登録・本登録の分離** | 「仮登録」のレコード作成日と「本登録」完了日が異なる場合、`created_at`だけでは本登録日が判定できなくなる。 |
| **予約・未来日付の扱い** | 予約投稿など「未来の日付」をドメインロジックに持たせたい場合、物理的なレコード作成日（`created_at`）では対応できない。 |

### 解決策
* **システム管理用の時間**（`created_at`、`updated_at`）と、**ドメイン用の時間**（`registered_at`、`published_at`、`ordered_at`など）は**完全に分離して別カラムにする**。
* `created_at`は「システムがレコードを物理的に挿入した時間」としてのみ扱い、ビジネスロジックの条件分岐（例：`where created_at >= ...`）には絶対に登場させない。
