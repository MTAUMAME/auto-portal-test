# クラウドにOSSを「持っていかれる」問題：Elastic、Redis、HashiCorpから考えるAGPLと岐路に立つ開発者たち

こんにちは、**Convergence Lab.** の管理人です。

ここ数年、テック業界を揺るがし続けているのが**「OSS（オープンソースソフトウェア）のライセンス変更問題」**です。

長年、エンジニアコミュニティに愛され、無償で利用されてきたソフトウェアたちが、次々と「ビジネスソースライセンス（BSL）」や「Server Side Public License (SSPL)」といった、**商業利用（特にクラウドベンダーによるホスティングサービス提供）を制限するライセンス**へと移行しています。

背景にあるのは、**「クラウドベンダー（AWS等）にタダで持って行かれ、マネタイズだけされる」**というOSS開発企業の悲痛な叫びです。

今回は、**Elastic、Redis、HashiCorp**の3事例を軸に、この問題の本質と「AGPL」の役割、そして私たちが今後選択すべき代替サービスや、自宅・検証環境で使えるおすすめガジェット・VPSまでを徹底解説します。

---

## 1. なぜライセンス変更が相次ぐのか？「持っていかれる」問題の構図

かつてOSSは、誰もが自由に使い、改良し、再配布できることが美徳とされてきました。しかし、AWSなどのメガクラウド事業者が登場したことで、ゲームのルールが変わりました。

```
【従来の構図】
OSS開発企業が開発 ──> ユーザーが利用（コミュニティが活性化・貢献）

【クラウド時代の歪み】
OSS開発企業が莫大なコストで開発 ──> クラウドベンダーが「マネージドサービス」として有料提供（利益の総取り） ──> 本家開発企業にお金が回らない
```

この「フリーライド（タダ乗り）」に対抗するため、企業はライセンスを以下のように変更していきました。

### 主要3社の動向

| 企業・プロジェクト | 元のライセンス | 変更後のライセンス | 主な代替・フォーク版 |
| :--- | :--- | :--- | :--- |
| **Elastic** (Elasticsearch) | Apache 2.0 | SSPL / ELv2 | **OpenSearch** (AWS主導) |
| **Redis** (Redis) | BSD (3-clause) | RSALv2 / SSPLv1 | **Valkey** (Linux Foundation主導) |
| **HashiCorp** (Terraform) | MPL 2.0 | BSL (Business Source License) | **OpenTofu** (Linux Foundation主導) |

*   **Elasticsearchの乱 (2021年):** AWSが「Amazon Elasticsearch Service」を販売し、莫大な利益を得たことに対し、ElasticがライセンスをSSPLに変更。AWSはこれに対抗し、Apache 2.0のままフォークした「OpenSearch」を立ち上げました。
*   **HashiCorpのBSL移行 (2023年):** Infrastructure as Code (IaC)のデファクトスタンダードであるTerraformがBSLへ移行。競合サービスを提供する企業がTerraformを直接商用利用できなくなり、コミュニティは反発。「OpenTofu」が誕生しました。
*   **Redisのライセンス変更 (2024年):** メモリ内データベースとして圧倒的人気を誇るRedisが、商用ホスティングを制限するライセンスへ変更。これに対し、Linux Foundationが中心となり、完全オープンソースの代替「Valkey」が爆誕しました。

## 2. 「AGPL（GNU Affero General Public License）」とは？

こうしたライセンス変更の中で、再び注目を集めているのが**「AGPL (v3)」**です。

GPLは「改変して配布する場合にソースコードの開示」を求めますが、クラウド（SaaS）のように「ネットワーク越しにサービスを提供する（配布はしない）」場合、コード開示義務を逃れることができました（いわゆるASPループホール）。

**AGPLは、このループホールを塞いだライセンスです。**
「ネットワーク経由でソフトウェアを利用させる場合も、改変したソースコードを公開しなければならない」という強力なコピーレフト性を持っています。

クラウドベンダーにとっては、自社のインフラ技術（プロプライエタリな部分）とAGPLのコードが混ざることで、自社コードの開示を迫られるリスクがあるため、**「最も嫌うライセンス」**の一つとされています。

## 3. 本家（商用・新ライセンス） vs フォーク（OSS・新プロジェクト）の比較

開発者やインフラエンジニアにとって、もっとも気になるのは**「このまま本家（マネージド）を使い続けるべきか、フォーク版（OpenSearch/OpenTofu/Valkey）に移行すべきか」**という点です。

ここでは、最もホットな **「Redis（本家）」と「Valkey（フォーク）」** を例に比較します。

### Redis vs Valkey 性能・コスト・移行性比較

| 比較項目 | Redis（本家・新ライセンス） | Valkey（Linux Foundation / OSS） |
| :--- | :--- | :--- |
| **ライセンス** | RSALv2 / SSPLv1 (商用制限あり) | BSD (3-clause) (完全オープン) |
| **ホスティング価格** | 本家マネージドやクラウド有料版（比較的高価） | AWS ElastiCache等で段階的にサポート（移行でコスト削減可） |
| **パフォーマンス** | 最新のRedis 8等は独自機能で高速化 | スレッドモデルの改善など、OSSコミュニティによる最適化が猛烈に進む |
| **ベンダーロックイン** | あり（ライセンス条項変更のリスクが残る） | なし（マルチクラウドに対応しやすい） |
| **移行の容易さ** | 既存コードをそのまま維持可能 | Redis 7.2互換。ドロップインで置き換え可能 |

**結論：**
自社でSaaSなどの商用サービスを提供している場合、将来的なライセンス違反リスクを避けるため、**「Valkey」や「OpenTofu」への移行を検討するのが2024年以降のスタンダード**になりつつあります。
