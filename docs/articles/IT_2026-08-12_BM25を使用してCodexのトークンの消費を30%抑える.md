## 1. なぜ「BM25」でCodexのトークンが削減できるのか？

### そもそもBM25とは？
BM25は、Googleなどの検索エンジンでもベースとして使われている**「キーワードベースの文書検索（情報検索）アルゴリズム」**です。与えられたクエリ（質問）に対して、どのドキュメント（コードスニペット）が最も関連性が高いかを高速かつ正確にスコアリングします。

### トークン削減の仕組み
CodexやGPTに「このコードのバグを直して」と頼む際、プロジェクト全体のファイルを丸ごとプロンプトに流し込むと、膨大なトークンを消費します。

1. **従来の方式**：関連しそうなコード（10,000トークン）をすべてLLMに送信 ➡️ **高コスト**
2. **BM25併用方式**：ローカルでBM25を実行し、クエリに関連する上位3ファイル（3,000トークン）だけを厳選してLLMに送信 ➡️ **30%〜70%のトークン削減！**

最新の「ベクトル検索（Embedding）」よりも軽量で、**サーバー代（API代）が一切かからないローカル処理が可能**な点が、BM25の最大の強みです。

## 2. 【性能・コスト比較】BM25 vs ベクトル検索 vs 生プロンプト

トークン削減手法としてよく比較される「生プロンプト（そのまま流し込み）」と「ベクトル検索（Embedding）」、そして「BM25」の3パターンを比較しました。

| 比較項目 | ① 生プロンプト（対策なし） | ② ベクトル検索（Dense Retrieval） | ③ BM25（ハイブリッド推奨） |
| :--- | :--- | :--- | :--- |
| **トークン消費量** | 100%（非常に多い） | 約30%〜50% | **約30%〜50%（30%以上の削減確定）** |
| **APIコスト** | 高い（従量課金が直撃） | 中（Embedding APIのコストが発生） | **極めて低い（ローカルで完全無料）** |
| **検索スピード** | なし（直接送信） | 低〜中（ベクトル化に時間がかかる） | **爆速（ミリ秒単位で処理完了）** |
| **キーワード一致精度** | N/A | 低（意味は捉えるが、完全一致に弱い） | **極めて高い（関数名や変数名に強い）** |
| **導入ハードル** | なし | 中（ベクトルDBの構築が必要） | **低い（Pythonの`rank_bm25`ライブラリで即実装）** |

### 結論
コード検索においては、「関数名」や「変数名」といった**厳密なキーワード一致**が重要になります。そのため、意味を曖昧に捉えるベクトル検索よりも、**BM25のほうがコーディングAI（Codex）への文脈提供において高い精度を発揮するケースが多い**のです。

## 4. 【簡単実装】BM25を試すためのPythonコード例

実際にBM25を使って、不要なコードをカットするPythonのミニマムコードです。

```python
from rank_bm25 import BM25Okapi

# 1. プロジェクト内のコードスニペット（コーパス）
code_snippets = [
    "def calculate_tax(price): return price * 0.1",
    "def connect_database(): db = MySQL.connect()",
    "def send_email(to, subject): smtp.send(to, subject)"
]

# 2. トークン化（簡易的にスペース分割。実用時は形態素解析やASTを推奨）
tokenized_corpus = [doc.split(" ") for doc in code_snippets]
bm25 = BM25Okapi(tokenized_corpus)

# 3. ユーザーの質問（クエリ）
query = "How to connect to database"
tokenized_query = query.split(" ")

# 4. 最も関連度の高いスニペットを1つだけ抽出（トークン制限に合わせる）
best_docs = bm25.get_top_n(tokenized_query, code_snippets, n=1)

print(best_docs)
# 出力: ['def connect_database(): db = MySQL.connect()']
# ➡️ これだけをCodexに送ることで、他の不要な2つの関数分のトークンを節約！
```
