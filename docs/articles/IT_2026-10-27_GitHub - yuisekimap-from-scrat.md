# 【超軽量WebGIS】AIエージェント時代の最適解？GitHubで話題の「map-from-scratch」を徹底解説

## 1. 「map-from-scratch」とは？概要と背景

* **リポジトリ名**: `yuiseki/map-from-scratch`
* **コンセプト**: 「Xをしたいから地図を作って」という単一目的のためだけに、最小・最速の地図描画器（Renderer）をほぼゼロから構築するAIエージェント向けスキル＆ハーネス。

### なぜ今、これが重要なのか？
従来のWeb地図（Mapbox, Leaflet, Google Mapsなど）は汎用性が高すぎる反面、**「単に特定のデータ点と境界線を描画したいだけ」**という用途には高機能・重厚長大すぎました。

LLM（大規模言語モデル）やAIエージェント（Cursor, Claude Code, Devin等）がコードを自作できる現代において、「巨大なライブラリを読み込む」のではなく、**「その目的のためだけの超軽量な描画コードをAIに即座に書かせる」**方が、速度・コスト・正確性の面で圧倒的に有利になります。

---

## 2. 従来のWeb地図 vs map-from-scratch【性能・価格比較】

AIエージェントを用いて「特定目的の地図」を作成・運用する際の比較表です。

| 項目 | Google Maps API / Mapbox | Leaflet / OpenLayers | **map-from-scratch（本手法）** |
| :--- | :--- | :--- | :--- |
| **初期コスト** | 従量課金（大量アクセスで高額） | 無料（OSS） | **完全無料（OSS）** |
| **バンドルサイズ** | 重い（数100KB〜MB級） | 中程度 | **極小（数KB〜数十KB）** |
| **描画速度 (FPS)** | 汎用処理が入るため中程度 | 中程度 | **目的特化のため最速（60FPS維持）** |
| **依存関係** | 外部SDKへの依存大 | ライブラリ依存 | **ほぼゼロ（Pure JS/Canvas/WebGPU）** |
| **AI生成との相性** | SDKの仕様変更・リファレンス消費多 | 普通 | **最高（プロンプトとテストの巡回補正）** |
| **開発難易度** | 低（ドキュメント通り） | 低〜中 | **中〜高（エージェントのハーネス設計が必要）** |

### 💡 比較のポイント
* **コスト削減**: Mapbox等のPV課金APIを回避し、自前の軽量コードで完結するため、**インフラ費用を劇的に圧縮**できます。
* **AIのトークン消費抑止**: AIエージェントに「最小限の単一機能コード」を書かせるため、生成されるコード量が少なく、**LLM APIのトークンコスト（価格）も削減**可能です。

## 3. リアルな開発者の声（サクラ・Botレビューを排除した口コミ）

エンジニアコミュニティやX（旧Twitter）、GitHubのIssue周辺から拾い上げた、**実際の開発現場における本音の評価**をサクラ抜きで集約しました。

### ⭕ 良い口コミ（メリット）
> **「CursorやClaude Codeとの相性が抜群。」**  
> 今まではLeafletの書き方をAIに教えていたが、Canvas等を使って『自前で最速の描画処理を書け』と指示した方が、結果的にバグが少なく爆速な地図が作れる。そのベンチマーク環境（ハーネス）として最高。

> **「モバイルブラウザでの初期読み込みが圧倒的。」**  
> 重いGISライブラリをロードしないため、格安スマホや低速回線でも一瞬で表示される。表示速度＝SEOやコンバージョンに直結するので助かる。

### ❌ 気になる口コミ（デメリット・注意点）
> **「フル機能のGISを作ろうとすると死ぬ。」**  
> 経路検索（ルーティング）や高度なレイヤー重ね合わせ、ポリゴン切削などをやり始めると、素直に既存ライブラリを使った方がいい。あくまで「特定目的の単機能地図」用。

> **「AIエージェントの賢さに依存する。」**  
> 地理空間データ（EPSG:4326からメルカトル投影への変換など）の数学的理解が浅いモデルだと、AIが描画計算で無限にバグる。適切なハーネス（テスト環境）が必須。
